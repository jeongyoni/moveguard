## 1. (0:00–0:40) 문제 제기

**화면** — 사업 목록 (<http://localhost:8080/>)

**내레이션**

> IDC에 있던 서버를 클라우드로 옮깁니다. 보통은 "옮기면 끝"이라고 생각하는데, 실제로는 옮기는 순간
> 안 뜨는 것들이 있습니다. WAS가 요구하는 자바 버전이 안 맞거나, 외부 기관 방화벽에 등록해둔
> 공인IP가 바뀌거나, 인증서가 전환 직후에 만료되거나.
>
> 문제는 이게 **전환 당일 새벽에 발견된다**는 겁니다. MoveGuard는 이걸 **이전하기 전에** 찾아내는 도구입니다.

**보여줄 것** — 사업 카드 한 줄: `쇼핑몰 서비스 클라우드 이전 · 가나다커머스 · IDC-A → AWS ap-northeast-2 · 전환 예정 2026-10-24`

> 이 사업은 2주 뒤 전환 예정입니다. 지금 이전하면 어떻게 되는지 진단해 보겠습니다.

## 2. (0:40–1:10) 진단 실행 → 판정

**조작** — `진단 실행` 클릭

**화면** — 결과 상단 판정 카드

**내레이션**

> 결과는 **HIGH, 전환 차단**입니다. 지금 상태로는 이전하면 안 된다는 뜻입니다.
>
> 최고 RPN 504, 종합 점수 35.1, 발견된 위험은 **15건**입니다.

**짚을 것 (판정 카드 수치)**

| 항목 | 값 | 의미 |
| --- | --- | --- |
| 위험 등급 | `HIGH` | 가장 위험한 항목의 RPN이 400 이상 |
| 전환 차단 | `차단` | **차단 규칙이 1건이라도 걸리면** 등급과 무관하게 차단 |
| 최고 RPN | `504` | 가장 위험한 항목(IP-04)의 점수 |
| 종합 점수 | `35.10` | 요인별 최고 RPN을 가중 합산 — 재진단 추이 비교용 |
| 발견 건수 | `16` | 규칙 22개 중 **14개**가 걸렸고, 자산별로 중복돼 총 16건 (CMP-05는 3건) |

**조작** — 판정 카드 아래 **`▸ 진단 입력 — 무엇을 보고 판단했나`** 를 펼친다

> 그런데 이게 뭘 보고 내린 판정인지부터 봐야겠죠. 여기 있습니다.
>
> 진단은 서버를 스캔하는 게 **아닙니다.** 이전 계획에 적힌 **이전 전 구성과 이전 후 구성을 비교**합니다.
> web01을 보면 Tomcat 9.0.80 → **11.0.22**, Java 1.8 → **11**, 공인IP 203.0.113.11 → 198.51.100.21.
> db01은 MySQL 5.7.44 → **9.6.1**이고, 이전 전에 있던 공인IP가 이전 후에는 **사라집니다.**
>
> 바뀌는 값이 주황색으로 표시돼 있는데, **바로 이 변화들이 판정의 재료**입니다.

**조작** — 입력 섹션을 다시 접는다

> 바로 아래 **위험요인별** 집계를 보면 어디가 문제인지 한눈에 보입니다.
> 공인IP·네트워크 4건, OS·DBMS 호환성 6건, 보안·접근통제 2건, DNS 1건, 백업·복구 2건.

## 3. (1:10–3:20) 발견 목록에서 4건 짚기 — 영상의 핵심

> 15건을 다 읽지 않는다. **아래 4건만** 짚는다. 각 카드의 RPN·제목·설명·조치를 그대로 읽으면 된다.

### 3-1. CMP-02 — "자바 버전이 안 맞아서 WAS가 안 뜬다" (RPN 270 · 전환 차단)

**화면** — CMP-02 카드로 스크롤

> **목표 WAS가 요구하는 최소 Java 버전 미달.**
> web01의 이전 후 Tomcat 11.0.22는 Java 17 이상이 필요한데, 이전 후 Java 버전은 11입니다.
> 이러면 애플리케이션이 뜨다 마는 게 아니라 **WAS 자체가 기동되지 않습니다.**
>
> 조치까지 같이 나옵니다 — "Java 런타임을 17 이상으로 올리거나, 현재 Java 버전을 지원하는 WAS 버전으로 목표를 조정하십시오."

**한 마디** — 이게 바로 전환 당일 새벽에 발견되면 가장 곤란한 종류의 문제다.

### 3-2. CMP-03 — javax → jakarta (RPN 378 · 전환 차단)

> **Tomcat 10부터 서블릿 패키지가 javax에서 jakarta로 바뀌었습니다.**
> web01이 Tomcat 9.0.80에서 11.0.22로 이전하는데, 이건 애플리케이션 코드를 고치지 않으면 기동되지 않습니다.
> 버전 숫자만 올리면 되는 게 아니라는 걸 진단이 잡아줍니다.

### 3-3. IP-04 — 외부 기관 방화벽 허용목록 (RPN 504 · 전환 차단, 최고점)

> **가장 위험한 항목입니다.**
> web01의 공인IP 203.0.113.11이 외부 기관 방화벽 허용목록에 등록돼 있는데, 이전 후 바뀝니다.
>
> 이건 우리가 고칠 수 있는 게 아니라 **외부 기관에 요청하고 기다려야 하는 일**입니다.
> 그래서 조치가 "사전 요청하고, **처리 기간을 전환 일정에 반영하라**"입니다. 전환 당일에 알면 늦습니다.

### 3-4. CERT-01 — 인증서 만료가 전환과 겹침 (RPN 192 · 전환 차단)

> shop.example.com 인증서가 **2026년 11월 10일 만료**인데, 전환 예정일이 10월 24일입니다.
> **전환하고 17일 뒤에 인증서가 만료**되는 겁니다. 전환 직후에 장애가 예약돼 있는 셈이죠.

**4건을 짚고 나서 전체를 한 번 훑으며**

> 나머지도 같은 형식입니다. IP 하드코딩, DNS TTL이 길어 전파가 늦는 문제, 백업 복구 테스트 미수행,
> 이전 후 백업 체계 미비까지 — **무엇이, 왜 위험하고, 무엇을 하면 되는지**가 전부 한 화면에 있습니다.

## 4. (3:20–4:10) 점수는 어떻게 매기는가

**화면** — 발견 목록 왼쪽의 RPN 숫자들, 그리고 `전환 차단` 배지

**내레이션**

> 이 점수는 임의로 정한 게 아니라 제조업 품질관리에서 쓰는 **FMEA** 방식입니다.
>
> **RPN = 심각도 × 발생가능성 × 검출난이도** — 최대 1000점입니다.
> 터졌을 때 얼마나 치명적인가, 실제로 일어날 확률이 얼마나 되는가, 미리 발견하기가 얼마나 어려운가.
> 세 가지를 곱하니까 "치명적이지만 쉽게 발견되는 것"보다 **"치명적이고 발견도 어려운 것"**이 위로 올라옵니다.
>
> 그리고 점수와 별개로 **차단 규칙**이 있습니다. 점수가 몇 점이든 이게 걸리면 전환 불가입니다.
> 지금 16건 중 **8건**이 차단 규칙입니다.

**추가로 말할 것**

> 규칙은 현재 **5개 위험요인에 20개**가 있고, 요인마다 가중치가 다릅니다.
> 공인IP·네트워크가 0.35로 가장 크고, 호환성 0.20, DNS·백업·보안이 각각 0.15입니다.
> 새 규칙은 판정기 클래스 하나와 DB 시드 한 줄만 추가하면 자동으로 붙습니다.

## 6. (4:50–6:00) 규칙이 얼마나 정확한가 — 검증과 학습

**내레이션(도입)**

> 여기서 당연한 질문이 나옵니다. **"그 규칙이 맞다는 근거는 뭐냐."**
> 실제 이전 성패 데이터가 없으니, 가상 이전사업을 대량으로 만들어서 측정했습니다.

**조작**

```bash
curl "http://localhost:8080/api/sim/analysis?count=2000&seed=42"
```

**화면/수치**

| 지표 | 값 | 해석 |
| --- | --- | --- |
| 재현율(recall) | **1.000** | 실제 실패하는 사업을 **하나도 놓치지 않았다** |
| 정밀도(precision) | **0.734** | 차단한 것 중 27%는 사실 성공했을 사업 — **과잉 차단** |
| F1 | 0.846 | |

> 재현율 1.0, 정밀도 0.73. 해석하면 **"규칙은 안전하지만 보수적"**입니다.
> 놓치는 건 없는데, 괜찮았을 사업도 막고 있다는 뜻이죠. 이걸 데이터로 확인한 겁니다.

**이어서 학습**

```bash
./ml/.venv/Scripts/python ml/train.py --count 6000 --seed 42
```

**출력** (표본 6000개, 특징 14개, 실패율 0.737)

| 모델 | 정밀도 | 재현율 | F1 | |
| --- | --- | --- | --- | --- |
| 규칙(baseline) | 0.739 | **1.000** | 0.850 | |
| LogisticRegression | 0.829 | 0.916 | **0.870** | ← baseline 초과 |
| RandomForest | 0.824 | 0.864 | 0.844 | |
| GradientBoosting | **0.838** | 0.906 | **0.871** | ← baseline 초과 |

> 규칙이 만든 결과는 학습에 넣지 않고 **원시 입력 특징만**으로 학습했습니다. 규칙을 베끼면 의미가 없으니까요.
> 결과는 ML이 **과잉 차단을 줄여서** F1에서 규칙을 넘어섭니다.
>
> 그렇다고 규칙을 버리는 게 아닙니다. **규칙은 "반드시 막아야 할 것"을, ML은 "우선순위와 예측"을** 맡는
> 하이브리드가 실무에 맞습니다. 규칙은 왜 막혔는지 설명할 수 있고, ML은 설명이 어렵기 때문입니다.

## 7. (6:00–6:45) 그래서 전환 당일은? — 전환 과정 시뮬레이션

**화면** — `des/video/cutover_2eng_HIGH.mp4` 재생 (84초짜리를 2배속으로 틀거나 앞부분만)

**내레이션**

> 마지막입니다. 진단이 HIGH로 나왔을 때, **전환 작업 자체가 정비창 안에 끝나는지**도 봤습니다.
> 자산 6대가 엔지니어 2명을 나눠 쓰면서 백업 → 서비스중단 → 데이터이전 → 재설정 → 검증을 거칩니다.

**화면에서 짚을 것** — 왼쪽에 쌓이는 대기열, 빨갛게 넘어가는 정비창 바

> 보시면 엔지니어 2명이 모두 작업 중이라 나머지 4대가 줄을 섭니다. 이게 병목입니다.
> 결과는 **8.4시간 — 정비창 6시간을 2.4시간 초과**했습니다. 롤백도 3건 났습니다.

**조작** — `cutover_4eng_LOW.mp4` 재생 (31초)

> 같은 속도로 돌린 영상인데 **길이가 3분의 1입니다.** 엔지니어 4명, 위험 LOW로 바꾸면
> 3.1시간에 끝나고 롤백은 0건입니다.

**500회 반복한 통계**

| 엔지니어 | 평균 소요 | 정비창(6h) 완료율 |
| --- | --- | --- |
| 2명 | 8.4h | **0.6%** |
| 3명 | 6.0h | 51% |
| 4명 | 5.2h | **87%** |

> 진단의 위험 등급이 이 시뮬레이션의 **실패 확률과 지연**으로 연결됩니다.
> HIGH면 검증 실패 확률 45%에 재설정이 1.7배 느려집니다.
> 그래서 **"진단이 HIGH다"가 곧 "그날 못 끝난다"**로 이어진다는 걸 숫자로 보여줄 수 있습니다.

## 8. (6:45–7:00) 마무리

> 정리하면 MoveGuard는
>
> **이전 전에 위험을 찾아내고(진단), 그 판정이 맞는지 데이터로 검증하고(시뮬·학습),
> 전환 당일 일정까지 추정합니다(DES).**
>
> 핵심은 "위험하다"가 아니라 **"무엇이 왜 위험하고 무엇을 하면 되는지"**를 준다는 점입니다.

## 부록 B. 예상 질문

| 질문 | 답 |
| --- | --- |
| 왜 규칙과 ML을 둘 다 쓰나 | 규칙은 **차단 근거를 설명**할 수 있고 확정적이다. ML은 우선순위·예측에 강하다. 막는 건 규칙, 예측은 ML. |
| 학습 데이터는 어디서 났나 | 실제 이전 성패 데이터가 없어 **시뮬레이션으로 합성**했다. 규칙 출력은 학습에 넣지 않아 순환을 피했다. |
| EOL 기준이 낡지 않나 | endoflife.date와 동기화하고, 네트워크가 없으면 번들 스냅샷으로 폴백한다. |
| GPU가 필요한가 | 표 데이터라 **CPU로 수 초**면 끝난다. GPU는 딥러닝·대규모 단계에서만 필요하다. |
| 규칙을 추가하려면 | `RiskRuleEvaluator` 구현체(@Component) + `risk_rule` 시드 한 줄. 자동으로 수집된다. |
| 왜 Arena가 아니라 SimPy/Salabim인가 | 모델은 같은 이산사건 시뮬레이션이다. Arena 모델 작성 절차는 `docs/ARENA_BUILD_STEPS.md`에 있고, 같은 분포로 만들어 결과를 교차 검증한다. |

## 부록 C. 기술 스택

- **백엔드**: Java 17 · Spring Boot 4.1 · MyBatis · MySQL 8.0 · Thymeleaf
- **진단 파이프라인**: 입력 로더 → `DiagnosisEngine`(규칙 평가 + RPN 정렬 + 점수) → 결과 화면/API/저장
- **시뮬·학습**: Java(`sim` 패키지 — 시나리오 생성·성패 라벨·규칙 분석) + Python(`ml/` scikit-learn, `des/` SimPy·Salabim)
