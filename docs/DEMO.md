# MoveGuard 데모 시나리오

발표/시연용 대본. 각 단계는 **명령 → 예상 출력 → 강조 포인트** 순서. 수치는 더미 사업(project 1) 기준.

---

## 0. 한 줄 소개

> **MoveGuard** — IDC → 클라우드 이전 시, 전환 위험을 **규칙으로 진단**하고 위험도를 산정해 **전환 가능/차단**을 알려주는 도구.
> 더 나아가 **시뮬레이션으로 데이터를 만들어 규칙을 검증·학습**하고, **전환 과정을 이산사건 시뮬레이션**으로 일정까지 추정한다.

데모 흐름: **진단 → 규칙 검증(시뮬) → 학습 → 전환 일정 시뮬**

---

## 1. 준비 (시연 전에 미리)

```bash
cd ~/dev/moveguard
docker compose up -d                 # MySQL (이미 떠 있으면 생략)
./gradlew bootRun                    # 앱 실행 — 이 터미널은 켜둔 채로
```
- 포트 8080. DB 시드는 이미 적용돼 있음(안 돼 있으면 README "스키마·시드 적용" 참고).
- 시연은 **새 터미널**(⌘+T)에서 curl, 또는 브라우저 주소창 사용.

---

## 2. 핵심 데모: 진단 실행

```bash
curl -X POST http://localhost:8080/api/projects/1/diagnoses
```

**예상 출력(요약):** `riskLevel: HIGH`, `blocked: true`, `maxRpn: 504`, 발견 **15건**
규칙 코드(위험 순): `IP-04 · IP-01 · CMP-03 · CMP-02 · PORT-01 · IP-03 · DNS-01 · BAK-02 · CERT-01 · IP-02 · CMP-05×3 · CMP-01 · BAK-03`

**강조 포인트**
- 자산의 네트워크·DNS·인증서·소프트웨어 버전·백업을 입력받아 **5개 위험요인**(네트워크/DNS/보안/호환성/백업)에서 **규칙 20개**로 판정
- 각 규칙은 FMEA **RPN = 심각도 × 발생 × 검출**로 점수화, **차단 규칙**이 하나라도 걸리면 전환 차단
- 단순 점수가 아니라 **"무엇이, 왜 위험한지 + 조치 가이드"** 를 함께 제시(응답의 message·mitigation)

---

## 3. 호환성 자동 동기화 (endoflife.date)

```bash
curl -X POST http://localhost:8080/api/compat/sync
```

**예상 출력:** 제품 14종(OS 8 + DB 3 + 서버앱 2 + 언어) 동기화 결과. 대부분 `LIVE`, java는 `SKIPPED`.

**강조 포인트**
- OS·WAS·DB의 **지원 종료(EOL)** 는 우리가 관리하지 않고 **endoflife.date와 동기화**해 최신 유지
- 네트워크가 안 되면 **번들 스냅샷으로 fallback** → 오프라인에서도 진단 동작
- 그래서 "MySQL 9.6은 이미 EOL", "Tomcat 11은 Java 17 필요" 같은 판정이 자동으로 최신 기준

## 4. 시뮬레이션 — 규칙이 얼마나 정확한가

### 4-1. 데이터셋 (가상 이전사업 생성 → 진단)
```bash
curl "http://localhost:8080/api/sim/dataset?count=20&seed=42"
```
→ 가상 사업마다 (입력 특징 + 진단 결과 + **실제 성패**) 한 줄씩 CSV.

### 4-2. 규칙 성능 분석
```bash
curl "http://localhost:8080/api/sim/analysis?count=2000&seed=42"
```
**예상 출력:** `precision 0.73`, `recall 1.00`, `f1 0.85`, 규칙별 실패 예측력(IP-01 0.95 … )

**강조 포인트**
- 가상 사업을 대량 생성해 진단 엔진에 통과시키고, **규칙의 예측 성능을 수치화**
- **재현율 1.0**(실패를 다 잡음) 이지만 **정밀도 0.73**(과잉차단) → "규칙은 안전하지만 보수적"임을 데이터로 증명
- 규칙별 실패 예측력 순위까지 제공 → 어떤 규칙이 진짜 중요한지

## 5. 학습 — ML이 규칙을 넘는가

```bash
./ml/.venv/bin/python ml/train.py --count 6000 --seed 42
```
**예상 출력:**
```
규칙(baseline)        정밀도 0.74  재현율 1.00  F1 0.85
LogisticRegression    0.83  0.92  0.87   <- baseline 초과
GradientBoosting      0.84  0.91  0.87   <- baseline 초과
```

**강조 포인트**
- 규칙 산출물은 빼고 **원시 입력 특징만**으로 성패를 학습 → 공정한 비교
- ML이 **과잉차단을 줄여(정밀도 ↑) F1에서 규칙을 초과** → "규칙이 못 잡는 패턴을 데이터가 보완"
- 표(tabular) 데이터라 **CPU 수 초** — GPU 불필요(대규모·딥러닝 때만)

## 6. 전환 과정 시뮬레이션 (이산사건, SimPy)

```bash
./des/.venv/bin/python des/cutover_sim.py --assets 6 --engineers 2 --risk HIGH --reps 500
./des/.venv/bin/python des/cutover_sim.py --fetch --project 1   # MoveGuard 진단과 연동
```

**예상 출력(엔지니어 수 민감도, HIGH·자산6·정비창6h):**

| 엔지니어 | 평균 소요 | 정비창 완료율 |
| --- | --- | --- |
| 2명 | 8.4h | 0.6% |
| 3명 | 6.0h | 51% |
| 4명 | 5.2h | 87% |

**강조 포인트**
- 전환(백업→중단→이전→재설정→검증→롤백)을 **이산사건 시뮬레이션**으로 모델링
- "정비창 안에 끝나는가?", "엔지니어 몇 명 필요?", "롤백 확률은?" 을 정량 추정
- `--fetch`로 **MoveGuard 진단 결과(riskLevel)를 시뮬 파라미터로 연결** → 진단과 일정 시뮬이 하나로

## 7. 마무리 멘트

- **진단(규칙)** → **검증·학습(시뮬+ML)** → **일정 시뮬(DES)** 까지, 이전 위험을 **판정하고·검증하고·예측**하는 한 바퀴를 구현
- 규칙은 안전하지만 보수적 → 데이터·학습으로 보완 가능함을 **수치로 입증**
- 확장 여지: 2차 범위(전환 실행·검증·롤백), 하이브리드 서빙(ML 예측을 진단 API에), 자산/시나리오 다양화

---

## 부록: 아키텍처 · 기술 스택

- **백엔드**: Java 17 · Spring Boot 4.1 · MyBatis · MySQL 8.0
- **진단 파이프라인**: 입력 로더 → `DiagnosisEngine`(규칙 평가+RPN 정렬+점수) → 결과/저장
- **시뮬·학습**: Java(`sim` 패키지, 데이터 생성·분석) + Python(`ml/` scikit-learn, `des/` SimPy)
- **규칙 추가가 쉬움**: `RiskRuleEvaluator` 구현체(@Component) + `risk_rule` 시드만 추가하면 자동 수집

## 부록: Q&A 대비

- **왜 규칙 + ML 둘 다?** 규칙은 설명가능·확정적(차단 근거 명확), ML은 우선순위·예측. 하이브리드가 실무형.
- **데이터는 어디서?** 실제 이전 성패 데이터가 없어 **시뮬레이션으로 합성** → 학습 데이터 공백 해결.
- **GPU/DGX 필요?** 현재 규모는 CPU로 충분. 딥러닝·대규모로 갈 때 DGX 활용(접속·빌드는 검증 완료).
- **EOL 기준이 낡지 않나?** endoflife.date 주기 동기화 + 오프라인 스냅샷 fallback.
