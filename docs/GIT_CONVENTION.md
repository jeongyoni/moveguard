# Git 규칙

## 작업 흐름

1. 이슈 생성: 무엇을, 왜 하는지와 완료 조건을 적는다
2. 브랜치 생성: `feature/<이슈번호>-<작업명>` (예: `feature/1-network-rules`)
3. 작업 및 커밋
4. Pull Request 생성: 본문에 `Closes #이슈번호`를 적어 병합 시 이슈가 자동으로 닫히게 한다
5. 테스트 통과 확인 후 `main`에 병합, 작업 브랜치 삭제

## 커밋 메시지

형식: `타입: 요약`

- 요약은 한글, 50자 이내, 끝에 마침표를 붙이지 않는다
- 설명이 필요하면 한 줄 띄우고 본문에 무엇을, 왜 바꿨는지 적는다

| 타입 | 용도 |
| --- | --- |
| feat | 새 기능 |
| fix | 버그 수정 |
| refactor | 동작 변경 없는 구조 개선 |
| test | 테스트 추가·수정 |
| docs | 문서 |
| chore | 설정, 빌드, 의존성 |
| style | 포맷팅 등 코드 의미에 영향 없는 변경 |

예시

~~~
feat: IP-04 외부 기관 허용목록 규칙 추가
fix: DNS 레코드가 없을 때 진단이 실패하는 문제 수정
refactor: 규칙 공통 로직을 DiagnosisContext로 이동
~~~

## 커밋 단위

- 한 커밋에는 하나의 의도만 담는다
- 테스트가 통과한 상태에서 커밋한다
- 커밋 전 `git status`로 변경 파일을 확인한다

## 브랜치

| 브랜치 | 용도 |
| --- | --- |
| `main` | 항상 빌드와 테스트가 통과하는 상태 유지 |
| `feature/<이슈번호>-<작업명>` | 기능 개발 |
| `fix/<이슈번호>-<작업명>` | 버그 수정 |

## 커밋하지 않는 파일

- 비밀번호·키가 들어간 설정: `application-local.yml`, `application-prod.yml`
- 빌드 결과물: `build/`
- IDE 설정: `.idea/`, `*.iml`
